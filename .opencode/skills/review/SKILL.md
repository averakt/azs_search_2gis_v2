# Review Skill

## Назначение

Ревью кода перед PR/merge/релизом: корректность, поддерживаемость, безопасность, производительность, соответствие архитектуре. Запускается **после** зелёных гейтов (tests/lint/build — см. `github`), не вместо них.

## Когда применять

- перед PR (по `PROJECT.md`/`AGENTS.md` — обязательно);
- перед merge изменений в общую ветку;
- перед релизом/деплоем;
- ревью архитектурно-значимого набора изменений.

## Когда НЕ применять

- сам этап написания кода → `development`;
- зелёные гейты ещё не пройдены — сначала `github` (тесты/линт/билд), потом ревью;
- чтение кода для своего понимания — это не ревью.

## Stance ревьюера

- Критикуешь код, не автора. Уважительно, по сути.
- Предполагаешь разумность автора, но проверяешь факты.
- Хвалим конкретное — «Positive observations» — это часть ревью, не вежливость.
- Различаешь **блокирующее** (надо исправить) и **предложение** (можно принять/отклонить с аргументом).

## Чеклист по областям

### Correctness
- Код делает то, что заявлено в PR-описании/плане.
- Edge cases: пустые входы, null/nil, нулевые/отрицательные значения, пустые коллекции, таймауты, ошибки внешних API (4xx/5xx).
- Ошибки не проглатываются (пустой `catch`, игнор `err`, `_` без лога).
- Деградация работает: отказ внешнего сервиса → предусмотренный fallback, не падение.
- Граничная логика (сортировки, лимиты, округления) корректна.

### Maintainability
- Имена понятны, функции не огромны, вложенность разумная.
- Нет дублирования логики (DRY), но и нет over-abstraction (YAGNI).
- Типы/контракты не размножены между слоями без нужды.
- Комментарии только по запросу проекта (правило: нет комментариев, если не просили).
- Код следует конвенциям проекта (стиль, структура каталогов, идиомы языка).

### Security
- Секреты — только env/менеджер секретов, не в исходниках/коммитах/ответах API.
- Входы валидируются на границе доверия.
- Нет инъекций (SQL-параметризация, экранирование вывода/шаблонизатор).
- Токены/ключи не логируются, не утекают в ответы клиенту.
- Внешние API: ToS-статус известен и зафиксирован (для неофициальных — пометка в UI/плане).

### Performance
- Нет лишних внешних запросов в цикле (N+1).
- Кэш используется по назначению; ключи/TTL корректны; дедупликация параллельных запросов.
- Внешние вызовы с таймаутами; соединения переиспользуются.
- Нет блокирующих операций в hot path; память не копируется без необходимости.
- Масштаб: для MVP — отметить «достаточно», не выдумать нагрузку.

### Architecture alignment
- Соответствует плану/ADR (если есть). Отклонение от плана — явно аргументировано в PR.
- Слои не нарушены (хендлер не лезет во внутренние модули напрямую; интерфейсы/контракты соблюдены).
- Нет «лишней сложности» ради гипотетического будущего (YAGNI).
- Внешние зависимости изолированы — заменимы.

## Уровни замечаний (severity)

| Уровень | Критерий | Действие |
|---|---|---|
| **Critical** | баг, дыра безопасности, падение, потеря данных, нарушение контракта/ToS | блокирует merge |
| **Major** | серьёзный дефект неблокирующий, плохая архитектура, заметный техдолг | блокирует merge, обсуждение решения |
| **Minor** | стиль, читаемость, мелкая оптимизация | предложить, автор решает |
| **Nit** | косметика (имя, пробел) | упомянуть опц., не требовать |

## Формат вывода ревью

```
## Critical
- [file:line] <проблема> → <ожидаемое>
## Major
- [file:line] <проблема> → <предложение>
## Minor
- [file:line] <замечание>
## Positive
- <что сделано хорошо>
## Вердикт
<Approve / Request changes / Comment>
```

Ссылки на код — в формате `file:line`, чтобы автор переходил. Конкретика важнее общих слов: не «обработай ошибки», а `path/to/file.go:42 — 429 не отдаёт stale-кэш, хотя план §4.6 требует`.

## Антипаттерны

- ревью без пройденных гейтов (тесты/линт/билд);
- общие замечания без `file:line`;
- микро-стилевые правки как Critical / Nit-шторм вместо сути;
- просить «используй библиотеку X» без проверки, что она в манифестах проекта;
- блокировать по гипотетическим сценариям без обоснования;
- ревью архитектуры после написания кода вместо этапа планирования (`architecture`);
- не отметить хорошее;
- навязывать идиомы другого языка/проекта.
