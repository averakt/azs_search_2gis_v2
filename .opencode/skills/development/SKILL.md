# Development Skill

## Назначение

Написание нового кода, реализация функций, исправление багов, рефакторинг — **после** архитектурного анализа (см. скилл `architecture`). Если задача крупная/неопределённая — сначала план, потом код.

## Когда применять

- реализация описанной в плане фазы;
- точечный багфикс;
- рефакторинг с понятной целью;
- добавление небольшой функции в существующую архитектуру.

## Когда НЕ применять

- задача требует проектного решения (выбор стека/хранилища/контракта) → `architecture`;
- тривиальная правка (опечатка, комментарий) → делай сразу, без скилла.

## Перед кодом — обязательно

1. Прочитать `README`, `PROJECT.md`/`AGENTS.md` (если есть) и план — стек, ограничения, фаза.
2. Найти связанные файлы (`grep`/`glob`), прочитать **соседний** код, чтобы повторить стиль.
3. Проверить, что предполагаемая библиотека уже используется в проекте (манифест: `package.json`, `go.mod`, `Cargo.toml`, `pyproject.toml`, `pom.xml`, `Gemfile` и т.п.) — **не вводить новую зависимость по умолчанию**.
4. Убедиться, что понимаешь текущую архитектуру: где живут аналогичные компоненты, как именуются файлы, какие конвенции (именование, структура каталогов, обработка ошибок, форматирование).
5. Не переписывать существующий рабочий код без необходимости — рефакторинг отдельной задачей, не вместе с фичей.

## Конвенции кода (языко-агностичные)

- Имена понятные, без сокращений кроме устоявшихся в проекте.
- Функции небольшие; вложенность разумная (если > ~4 уровней — извлекай).
- Нет magic numbers — именованные константы.
- Нет кода «на потом» (закомментированного, `TODO` без контекста) — либо задача в трекере, либо удали.
- **Комментарии — только если попросили** (правило проекта).
- **Следуй идиомам языка и конвенциям проекта**, а не своим привычкам: если проект на Go — `gofmt` и `error wrapping`; если на Python — PEP 8 и существующий линтер; если на TS — `tsconfig` проекта. Не тащи стиль из другого языка.

## Обработка ошибок

- Все внешние сущности (сеть, БД, внешние API, пользовательский ввод) — ненадёжны. Обрабатывать явно.
- Пользователю — понятное сообщение, не внутренности/стек-трейс.
- В лог — контекст: что, где (`file:line`/операция), исходная ошибка.
- Различать **ожидаемые** ошибки (валидация → 4xx, человекопонятное) и **неожиданные** (→ 5xx, лог с уровнем error).
- Деградация: при отказе внешнего сервиса — отдавать заглушку/кэш, не ронять приложение (см. `architecture`, System Design → деградация).
- Не проглатывать ошибки молча (пустой `catch`, игнор `err`, `_`) без явного обоснования.

## Безопасность

- Входные данные валидируются на границе доверия.
- Секреты — только через env/менеджер секретов, **никогда** в исходниках/коммитах.
- Не логировать токены, ключи, PII.
- SQL — только параметризованные запросы; вывод — экранирование/шаблонизатор.
- Проверять: не утекают ли ключи внешних API в ответ клиенту.

## Зависимости

Добавлять новую — только если:
- нет подходящей в проекте;
- она поддерживается, не заброшена;
- лицензия совместима;
- выгода превышает риск цепочки поставок.

Перед добавлением — назвать причину в PR-описании.

## Чеклист завершения

- [ ] Тесты проекта зелёные (команду определи из `Makefile`/`package.json`/`README`).
- [ ] Линт проекта зелёный.
- [ ] Билд проекта зелёный.
- [ ] Нет закомментированного/debug-кода (временные логи, отладочные принты).
- [ ] Нет секретов в diff.
- [ ] Затронутые точки из плана отмечены.

## Антипаттерны

- писать код до чтения соседних файлов/`README`/`PROJECT.md`;
- вводить зависимость «потому что удобно»;
- смешивать рефакторинг и фичу в одном PR;
- молча проглатывать ошибки;
- оставлять `TODO` без ссылки на задачу;
- тащить идиомы другого языка в текущий стек;
- игнорировать таймауты/контексты в внешних вызовах.
