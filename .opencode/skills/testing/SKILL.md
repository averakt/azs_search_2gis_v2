# Testing Skill

## Назначение

Написание тестов, проверка изменений, разбор упавших тестов, верификация качества перед PR.

## Когда применять

- после реализации фичи/багфикса (до PR — обязательно);
- при разборе падающего теста;
- при изменении логики, которая покрыта/должна быть покрыта тестами.

## Когда НЕ применять

- тривиальная правка (комментарий, форматирование) — тесты не нужны;
- чисто архитектурный план — тесты пишет имплементатор;
- исследовательский спайк — фиксируем факт, не тест-сьют.

## Определи тест-стек проекта

Прочитай манифесты и `README`/`Makefile`: какой раннер и библиотека утверждены в проекте (напр. `go test`, `pytest`, `vitest`/`jest`, `cargo test`, `JUnit`, `rspec`). **Используй то, что уже есть** — не вводи новый фреймворк без причины. Команду запуска тестов/покрытия бери из проекта.

## Пирамида тестов

1. **Unit (большинство)** — чистая логика: маппинг/преобразование данных, кэш (TTL/инвалидация), эвристики, бизнес-правила, расчёты.
2. **Integration (умеренно)** — хендлеры/эндпоинты с моком внешних зависимостей; компоненты UI с моком API.
3. **E2E (минимум)** — ключевой сценарий через собранное приложение; дорого, держать 1–3.

## Что тестировать (приоритет)

- **Критическая логика** (обязательно): маппинг внешних ответов → доменные типы, кэш (hit/miss/expiry), деградация при ошибках внешних сервисов (4xx/5xx/timeout), валидация входов, сортировки/ограничения.
- **Бизнес-правила** (обязательно): эвристики, преобразования единиц/типов, округления.
- **Не тестировать**: тривиальные getter/setter, маппинги 1:1, чужой код из библиотек.

## Свойства хороших тестов

- Независимые — порядок запуска не важен, общий state через setup/teardown.
- Детерминированные — время/случайность через инъекцию (fake clock, seeded rand); **без** sleep без необходимости.
- Быстрые — unit < ~100мс; integration < ~1с; E2E отдельно.
- Имена описывают сценарий, не `test1`.
- Один тест — одно поведение; assert минимально достаточны.
- Arrange-Act-Assert структура видна.

## Разбор падающего теста

1. Прочитать сообщение и стек — локализовать падающий assert.
2. Воспроизвести локально (команда раннера проекта, фильтр по тесту).
3. Определить: **баг в коде** или **тест устарел/недетерминирован**.
4. Минимальный тест-кейс, воспроизводящий проблему (уменьшить вход).
5. Если баг в коде — сначала тест, ловящий его (красный), потом фикс (зелёный). Если тест устарел — обновить контракт, объяснить почему.
6. Перепроверить смежные сценарии (регрессия).
7. Не отключать тест (skip/`@Ignore`/`pytest.mark.skip`) без причины в коммите/PR.

## Покрытие

- Не гнаться за процентом. Цель — критическая логика и бизнес-правила покрыты.
- Coverage-метрику использовать как подсказку, не как KPI.
- Непокрытые ветки ошибок (timeout/5xx/границы) — важнее, чем happy path.

## Flaky-тесты

- Flaky = баг в тесте, не «особенность». Чинить сразу, не игнорировать.
- Частые причины: время (системный `now` без fake), порядок, shared state, race condition. Включать детектор гонок в CI, если язык поддерживает (`-race`, TSAN).

## Перед PR (по `PROJECT.md`/`AGENTS.md`)

- [ ] Тесты проекта зелёные.
- [ ] Добавлены тесты на новую/изменённую критическую логику.
- [ ] Нет закомментированных/отключённых тестов без причины.

## Антипаттерны

- тесты только на happy path;
- мокать то, что не нужно (мок ради мока);
- `sleep` вместо fake clock;
- assert на внутреннее состояние вместо поведения;
- тест зависит от порядка запуска;
- гонка за 100% coverage бесполезными тестами;
- коммитить упавший/отключённый тест;
- вводить новый тест-фреймворк вместо существующего.
