# GitHub Skill

## Назначение

Git-операции, подготовка коммитов и PR, pre-merge верификация. Покрывает локальный git и GitHub через `gh`.

## Когда применять

- коммит набора изменений;
- подготовка и создание PR;
- pre-merge проверка ветки;
- работа с issues/PR через `gh`.

## Когда НЕ применять

- распаковка/чтение истории для анализа — делай напрямую `git log`/`git diff` без скилла;
- архитектурное планирование → `architecture`;
- сам код-ревью → `review`.

## Перед коммитом

- `git status` — что в staging/working tree.
- `git diff` (staged + unstaged) — содержательно ли, нет ли лишнего.
- `git log -5 --oneline` — повторить стиль сообщений проекта.
- Убедиться: **нет секретов** в diff (`.env`, ключей, токенов); нет debug-кода (временные логи/принты); нет временных/мусорных файлов; нет огромных сгенерированных файлов без `.gitignore`.

## Правила коммитов

- Один коммит — одна логическая задача. Не смешивать фичу и рефакторинг.
- Атомарность: каждый коммит собирается (билд проекта) зелёным.
- **Conventional Commits**, если в проекте нет иного соглашения (проверь `git log`):

  | Тип | Когда |
  |---|---|
  | `feat:` | новая функция |
  | `fix:` | исправление бага |
  | `refactor:` | рефакторинг без изменения поведения |
  | `test:` | добавление/правка тестов |
  | `docs:` | документация |
  | `chore:` | сборка, зависимости, конфиг |
  | `perf:` | производительность |

- Заголовок < 72 символов, повелительное наклонение (`add`, не `added`).
- Тело (опц.): **почему** изменение (not **что** — видно из diff), ссылка на задачу/ADR.
- Не коммитить пустые коммиты (`--allow-empty`) без причины.

## Ветвление

- Именование: `<type>/<кратко>-<issue>` или `<type>/<кратко>`, напр. `feat/checkout-flow`, `fix/stale-cache`.
- Короткоживущие ветки; ребейз на базу перед PR если возможно.
- Не коммитить напрямую в `main`/`master` без явного согласия.

## Pull Request

### Шаблон описания

```
## Что делает
<1–3 пункта>

## Почему
<мотивация / ссылка на план или ADR>

## Как проверено
- [ ] tests
- [ ] lint
- [ ] build
- [ ] manual: <сценарий>

## Риски / совместимость
<если есть>
```

### Pre-merge гейты (по `PROJECT.md`/`AGENTS.md` — все обязательны)

- [ ] Тесты проекта зелёные (команду определи из `Makefile`/`package.json`/`README`).
- [ ] Линт проекта зелёный.
- [ ] Билд проекта зелёный.
- [ ] код прошёл review (скилл `review`).
- [ ] нет секретов, debug-кода, лишних файлов.

### Создание PR

- `gh pr create` с заголовком в стиле проекта и телом по шаблону выше (heredoc).
- Базовая ветка — `main` (или `develop`, если есть).
- Связать с issue (`Closes #N`), если есть.

## Git Safety — запреты без явного запроса пользователя

- **Никогда**: `git push --force` (особенно в `main`/`master`), `git reset --hard` к чужим коммитам, `git push --no-verify` (обход хуков), `--no-gpg-sign`, удаление remote-веток, `git rebase -i` (интерактив).
- **Никогда** не менять `git config` (user/email/keys).
- **Не** амендить (`--amend`) уже опубликованный коммит.
- Коммит — только по явному запросу пользователя. PR и push — только по явному запросу.
- Любое деструктивное/необратимое действие — сначала предупредить и получить подтверждение.

## Слияние

- По умолчанию — squash-merge в `main` (один чистый коммит), если в проекте нет иного соглашения.
- Удалять feature-ветку после merge (через `gh pr merge --delete-branch`), если не нужна.

## Антипаттерны

- коммитить secrets/`.env`;
- огромный PR (> ~400 строк логики без разбиения) — дробить;
- один PR на несколько независимых задач;
- коммитить закомментированный/debug-код;
- пушить без пройденных гейтов;
- `--force` в общую ветку;
- игнорировать `git status`/`git diff` перед коммитом;
- придумывать стиль коммитов вместо повторения `git log`.
