# Architecture Skill

## Назначение

Проектирование новых систем и функций, архитектурные изменения, важные технические решения **до написания кода**.

## Когда применять

- создаёшь новую систему или крупный модуль;
- меняешь архитектуру существующего решения;
- принимаешь решение, которое дорого откатить (выбор стека, хранилища, внешнего API, контракта);
- задача с внешними зависимостями/неопределённостью в данных.

## Когда НЕ применять

- точечное изменение в рамках существующей архитектуры → `development`;
- тривиальная задача (< 3 шагов);
- чисто информационный запрос без проектного решения.

## Главное правило

Не начинать реализацию сложных изменений без предварительного анализа.
Анализ ≠ «подумать и написать код». Анализ = зафиксировать требования, ограничения, риски и решение в виде артефакта.

## Определи контекст проекта (первым делом)

Прочитай файлы проекта, если есть: `README`, `PROJECT.md`/`CONTRIBUTING.md`, `AGENTS.md`, манифесты зависимостей (`package.json`, `go.mod`, `Cargo.toml`, `pyproject.toml`, `pom.xml`, `build.gradle`, `Gemfile`, `composer.json` и т.п.), конфиги линтеров, `Makefile`. Извлеки: стек, конвенции, ограничения, workflow. **Не предполагай стек — определи его.**

---

## Фаза 1. Анализ (до решений)

1. **Требования** — что система должна делать; явные и неявные ограничения (производительность, бюджет, ToS, сроки).
2. **Ограничения** — технические, правовые, ресурсные. Выписать явно.
3. **Существующая архитектура** — затронутые компоненты, где они живут (`file:line`).
4. **Внешние зависимости** — **верифицировать живые источники**, не полагаться на assumptions: проверить реальную доступность API/данных запросом или перехватом, зафиксировать endpoint/авторизацию/схему/лимиты. Это самый частый источник провала — делать обязательно для внешних интеграций.
5. **Развилки** — решения, которые требует выбора заказчика. Вынести в вопросы с рекомендацией.

## Фаза 2. System Design

Описать (применимо к задаче — не раздувать ради полноты):

- **компоненты** и их ответственность;
- **поток данных** (вход → преобразование → выход, стрелками или шагами);
- **внешние сервисы** — какие, зачем, fallback при недоступности;
- **API** — endpoints, request/response, ошибки, auth;
- **хранение данных** — см. Data Design;
- **масштабирование** — только если релевантно (MVP → отметить «не требуется»);
- **деградация** — что получает пользователь при отказе каждого внешнего зависимого сервиса.

## Фаза 3. Architecture Decisions

Каждое важное решение — в формате ADR (Architecture Decision Record). Кратко, по шаблону:

```
### ADR-N: <название>
Decision: что принято.
Reason: почему.
Alternatives: что рассматривалось (1–2 варианта).
Trade-offs: компромиссы.
```

Решение без `Alternatives` и `Trade-offs` — не решение, а выбор по инерции.

## Фаза 4. Data Design

- **структура** — доменные типы/схемы таблиц/ключи кэша;
- **связи** — между сущностями;
- **целостность** — инварианты, что не должно случиться;
- **производительность** — индексы/ключи кэша/TTL, ожидаемые объёмы;
- **миграции** — если меняешь существующую схему; для MVP без БД — явно указать «не требуется» и описать стратегию кэша (ключи, TTL, инвалидация).

## Фаза 5. Security

Явно по пунктам (для пет-проекта — пометить уровень, но не пропускать):

- **authn/authz** — кто куда может;
- **secrets** — где хранятся, как попадают в runtime, что НЕ в репо;
- **input validation** — границы доверия на входе;
- **data exposure** — что отдаём наружу, не утекают ли ключи/PII;
- **внешние API и ToS** — статус лицензирования/ToS, риски.

## Фаза 6. План реализации

- разбивка на фазы с явной **первой блокирующей** (обычно де-риск главного неизвестия — внешнего API/данных);
- каждая фаза — измеримый результат (артефакт или зелёный критерий);
- критерии приёмки всего решения.

---

## Выходной артефакт

Результат — документ (для крупных задач — файл в репо, напр. `IMPLEMENTATION_PLAN.md` или `docs/ADR/*.md`). Содержит:

1. Краткое описание цели.
2. Зафиксированные решения (таблица от заказчика).
3. Опорные факты ресёрча (ссылки, endpoint-ы, ограничения) — **передаваемые имплементатору**, чтобы не дублировать ресёрч.
4. Архитектура (компоненты, поток данных, API, хранение, деградация).
5. ADR по каждому важному решению.
6. Data Design + Security.
7. План реализации по фазам.
8. Критерии приёмки.
9. Риски и митигация.
10. Ссылки/источники.

Документ должен быть **самодостаточен** для модели-имплементатора.

## Антипаттерны

- начинать с кода без артефакта анализа;
- решений без `Alternatives`/`Trade-offs`;
- assumptions о внешних API без живой проверки (перехват/запрос);
- раздувать все разделы на тривиальной задаче (отмечай «не требуется» вместо пустого);
- плодить ссылки на «изучи существующую архитектуру» без `file:line`;
- предполагать стек вместо чтения манифестов проекта.

## Границы скилла

Скилл описывает **как проектировать**, а не конфигурацию проекта (модели/этапы/quality gates лежат в `PROJECT.md`/`AGENTS.md`). Не дублировать сюда workflow — это не задача архитектурного скилла.
